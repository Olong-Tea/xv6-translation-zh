# 2.7 安全模型 (Security Model)

你可能会想，操作系统是如何处理充满 Bug 或恶意的代码的。因为应对恶意行为绝对比处理偶然的 Bug 更困难，所以将主要精力集中在提供防御恶意行为的安全机制上是合理的。以下是操作系统设计中典型的安全假设和目标的高层视角。

操作系统必须假设，进程的用户级代码会竭尽全力去破坏内核或其他进程。用户代码可能会尝试解引用（dereference）其允许的地址空间之外的指针；它可能会试图执行不打算给用户代码执行的指令；它可能会尝试读写 RISC-V 的控制寄存器；它可能会试图直接访问设备硬件；它还可能向系统调用传递极其巧妙的值，试图欺骗内核使其崩溃或做出愚蠢的行为。

内核的目标是限制每一个用户进程，使其只能访问自己的用户内存、使用 32 个 RISC-V 通用寄存器，并且只能以系统调用所允许的方式来影响内核和其他进程。内核必须阻止任何其他越界行为。这通常是内核设计中的绝对要求。

但对内核自身代码的期望则完全不同。内核代码被假定是由善意且谨慎的程序员编写的，是无 Bug 的，并且不包含任何恶意内容。这种假设会影响我们分析内核代码的方式。例如，有许多内部的内核函数（比如自旋锁，`spin locks`），如果内核代码错误地使用它们，将会导致严重的问题。然而，我们假设内核能够正确地使用它自己的函数。在硬件层面，我们假设 RISC-V CPU、RAM、磁盘等都能按照文档声明的那样正常运行，不存在硬件 Bug。

现实世界却并非如此简单。要阻止滥用的用户程序以消耗内核保护资源（如磁盘空间、CPU 时间、进程表槽位等）的方式疯狂调用系统调用，从而导致系统瘫痪（拒绝服务），是非常困难的。编写 100% 无 Bug 的内核代码或设计无 Bug 的硬件通常也是不可能的；如果恶意用户代码的编写者察觉到了内核或硬件的 Bug，他们一定会加以利用。即使是在 Linux 这样成熟且被广泛使用的内核中，人们也经常会发现以前未知的漏洞（vulnerabilities）[^1]。最后，用户代码和内核代码之间的界限有时是模糊的：一些享有特权的用户级进程可能会提供基本服务，并在实际上成为操作系统的一部分；在某些操作系统中，享有特权的用户代码甚至可以向内核中插入新代码（就像 Linux 的可加载内核模块和 eBPF 一样）。

作为对内核 Bug 的部分防御措施，xv6 代码包含了对不一致性（inconsistencies）和不可恢复错误的检查机制，并在遇到这些情况时会调用 `panic()` 作为响应。该函数会打印一条错误消息并直接让系统停机（halt）。触发 Panic 并不是我们希望看到的结果，但总比在错误状态下继续执行要好。通常，Panic 是由内核 Bug 引起的，这些 Bug 会导致内核数据出错，或者导致内核执行非法操作（例如引用了不存在的内存）；在这种情况下，通过 `panic()` 让系统停机，比试图在不一致的状态下继续运行要安全得多。内核开发人员对 Panic 的反应，应该是努力查明并修复底层的代码 Bug。
