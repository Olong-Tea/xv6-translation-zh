# 2.3 内核架构 (Kernel organization)

一个核心的设计问题是：操作系统的哪些部分应该在监管者模式（supervisor mode）下运行？一种可能性是让整个操作系统都驻留在内核中，这样所有系统调用的实现都在监管者模式下运行。这种组织架构被称为**宏内核（单体内核，monolithic kernel）**。

在宏内核架构中，整个操作系统由一个在监管者模式下运行的单一程序组成。这种架构之所以方便，原因之一是操作系统设计者不需要绞尽脑汁将代码划分为“需要监管者特权”和“不需要监管者特权”的两部分。此外，由于操作系统的各个部分都属于同一个程序，它们之间的协作非常容易。例如，一个宏内核可以将磁盘块缓存（disk block cache）同时与文件系统和虚拟内存系统共享。

这种架构的缺点是，宏内核往往会变得庞大且复杂，以至于没有任何一个开发者能够完全理解代码不同部分之间的所有交互；这简直就是滋生 Bug 的温床。内核中的 Bug 尤其麻烦，因为它可能会导致整台计算机崩溃，或者导致许多应用程序出现故障，亦或是让整台计算机容易遭受安全攻击。

**微内核（microkernel）** 旨在降低内核中出现 Bug 的概率。它的核心思想是：将尽可能少的功能放入内核本身，使得在监管者模式下执行的代码非常少，从而使内核变得容易理解，并易于进行正确性分析。操作系统的绝大多数功能都作为用户级（user-level）服务器进程运行。例如，文件系统代码将作为服务器进程在用户模式（而非监管者模式）下执行。

图 2.1 展示了这种微内核设计。图中，文件系统作为一个用户级服务器进程运行。为了允许应用程序与文件服务器进行交互，内核提供了一种进程间通信（IPC）机制，用于将消息从一个用户模式进程发送到另一个进程。例如，如果像 shell 这样的应用程序想要读取或写入文件，它会向文件服务器发送一条消息，然后等待响应。

在微内核中，内核接口由少数几个底层函数组成，用于启动应用程序、发送消息、访问设备硬件等。这种架构使得内核相对简单，因为操作系统的绝大部分都驻留在用户级服务器中。

在现实世界中，宏内核和微内核都很流行。许多 Unix 内核都是宏内核。例如，Linux 就拥有一个宏内核，尽管它的某些操作系统功能（比如窗口系统）是作为用户级服务器运行的。Linux 能够为重度依赖操作系统的应用程序提供极高的性能，部分原因就在于其内核的各个子系统能够被极其紧密地集成在一起。

像 Minix、L4 和 QNX 等操作系统则是以“微内核+服务器”的架构组织的，并在嵌入式环境中得到了广泛部署。L4 的一个变种 seL4 非常小巧，以至于人们能够对其内存安全性和其他安全属性进行数学形式化验证 [^8]。

操作系统开发者之间关于哪种架构更好的争论由来已久（译者注：最著名的便是 Linus 与 Tanenbaum 的论战），但至今也没有决定性的证据能证明其中一方绝对优于另一方。此外，这在很大程度上取决于“更好”究竟意味着什么：是更快的执行性能、更小的代码体积、内核本身的可靠性，还是整个操作系统（包括用户级服务在内）的整体可靠性？

还有一些现实的考量可能比“选择哪种架构”的问题更为重要。某些操作系统虽然采用了微内核架构，但出于性能原因，却在内核空间中运行了一些用户级服务。而有些操作系统采用宏内核仅仅是因为它们一开始就是这么设计的，并且几乎没有动力去重构为一个纯粹的微内核架构——因为开发新功能往往比彻底重写现有操作系统以适应微内核设计更重要。

从本书的视角来看，微内核和宏内核操作系统共享了许多核心理念。它们都需要实现系统调用、使用页表、处理中断、支持进程机制、使用锁进行并发控制、实现文件系统等等。本书将重点关注这些通用的核心理念。

xv6 被实现为一个宏内核，就像大多数 Unix 操作系统一样。因此，xv6 的内核接口就对应着操作系统的接口，且内核实现了完整的操作系统功能。由于 xv6 提供的服务并不多，它的内核代码甚至比某些微内核还要小，但在概念上，xv6 绝对是宏内核。
