# 1.3 管道 (Pipes)

管道（pipe）是一个小型的内核缓冲区，它以一对文件描述符的形式暴露给进程：一个用于读取，另一个用于写入。将数据写入管道的一端，就可以从管道的另一端读取该数据。管道为进程提供了一种通信方式。

下面的示例代码运行了 `wc` 程序，并将其标准输入连接到了管道的读取端。

```c
int p[2];
char *argv[2];

argv[0] = "wc";
argv[1] = 0;

pipe(p);
if(fork() == 0) {
  close(0);
  dup(p[0]);
  close(p[0]);
  close(p[1]);
  exec("/bin/wc", argv);
} else {
  close(p[0]);
  write(p[1], "hello world\n", 12);
  close(p[1]);
}
```

该程序调用 `pipe`，创建了一个新管道，并将用于读取和写入的文件描述符记录在数组 `p` 中。在 `fork` 之后，父进程和子进程都拥有了指向该管道的文件描述符。子进程调用 `close` 和 `dup` 将文件描述符 `0`（标准输入）指向管道的读取端，然后关闭 `p` 中的原始文件描述符，并调用 `exec` 运行 `wc` 程序。当 `wc` 尝试从其标准输入读取数据时，它实际上是在从管道中读取。父进程则关闭管道的读取端，向管道写入数据，然后关闭写入端。

如果没有可用数据，对管道的 `read` 操作将会等待（阻塞），直到有数据被写入，或者所有指向管道写入端的文件描述符都被关闭；在后一种情况下，`read` 将返回 0，就像读取到了数据文件的末尾一样。正因为 `read` 会一直阻塞直到不可能再有新数据到达，所以在上述代码中，**子进程在执行 `wc` 之前关闭管道的写入端非常重要**：如果 `wc` 的某个文件描述符一直指向管道的写入端，那么 `wc` 将永远无法看到文件结束标志（end-of-file）。

xv6 的 shell 以类似于上述代码的方式实现管道线命令 (7950)，例如 `grep fork sh.c | wc -l`。子进程创建一个管道，用于连接管道线的最左端和最右端。然后，它为管道线的左端调用 `fork` 和 `runcmd`，并为右端同样调用 `fork` 和 `runcmd`，接着等待两者完成。管道线的右端本身可能也是一个包含了管道的命令（例如 `a | b | c`），它自己会再次 `fork` 出两个新的子进程（一个给 `b`，一个给 `c`）。因此，shell 可能会创建出一棵进程树（tree of processes）。这棵树的叶子节点是具体的命令，而内部节点则是那些等待其左右子进程完成的后台进程。

管道看起来似乎并不比临时文件更强大。例如，以下管道线：

```bash
echo hello world | wc
```

可以不使用管道，而是通过临时文件来实现：

```bash
echo hello world >/tmp/xyz; wc </tmp/xyz
```

但在这种场景下，管道相对于临时文件至少有三个显著优势：

1. **管道会自动清理自身。** 如果使用文件重定向，shell 必须在执行完毕后小心翼翼地删除 `/tmp/xyz`。
2. **管道可以传递任意长度的数据流。** 而文件重定向则要求磁盘上必须有足够的空闲空间来存储所有被重定向的数据。
3. **管道允许管道线的各个阶段并行执行（parallel execution）。** 而使用文件的方法则要求第一个程序必须完全结束，第二个程序才能开始运行。
