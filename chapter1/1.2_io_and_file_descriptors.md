# 1.2 I/O 与文件描述符 (I/O and File descriptors)

**文件描述符 (file descriptor)** 是一个小整数，它代表了一个由内核管理的对象，进程可以从该对象中读取数据或向其写入数据。进程可以通过打开文件、目录或设备，或者通过创建管道（pipe），抑或是复制一个已存在的文件描述符来获取它。为了简单起见，我们通常将文件描述符所指向的对象统称为“文件”；文件描述符接口屏蔽了文件、管道和设备之间的底层差异，使它们看起来都像是字节流（streams of bytes）。我们将输入和输出统称为 **I/O**。

在内部，xv6 内核使用文件描述符作为单进程表格（per-process table）的索引，因此每个进程都拥有一个从 0 开始的私有文件描述符空间。按照惯例，进程从文件描述符 `0`（标准输入, standard input）读取数据，将输出写入文件描述符 `1`（标准输出, standard output），并将错误信息写入文件描述符 `2`（标准错误, standard error）。正如我们稍后将看到的，shell 正是利用这一惯例来实现 I/O 重定向和管道的。shell 会确保它始终打开着三个文件描述符 (8007)，在默认情况下，这三个描述符都指向控制台（console）。

`read` 和 `write` 系统调用负责从文件描述符命名的已打开文件中读取字节或写入字节。`read(fd, buf, n)` 调用最多从文件描述符 `fd` 中读取 `n` 个字节，将它们复制到 `buf` 中，并返回实际读取的字节数。每个指向文件的文件描述符都关联着一个**偏移量 (offset)**。`read` 会从当前文件偏移量处开始读取数据，然后将该偏移量向前推进所读取的字节数：因此，后续的 `read` 调用将会返回紧接着前一次 `read` 返回数据之后的字节。当没有更多字节可读时，`read` 返回 `0` 以指示到达文件尾（end of the file）。

`write(fd, buf, n)` 调用将缓冲区 `buf` 中的 `n` 个字节写入文件描述符 `fd`，并返回实际写入的字节数。只有在发生错误时，写入的字节数才会少于 `n`。与 `read` 类似，`write` 会在当前文件偏移量处写入数据，然后将该偏移量向前推进所写入的字节数：每一次 `write` 都会从上一次写完的位置继续往下写。

下面的程序片段（构成了 `cat` 程序的核心逻辑）将数据从其标准输入复制到标准输出。如果发生错误，它会将错误信息写入标准错误。

```c
char buf[512];
int n;

for(;;){
  n = read(0, buf, sizeof buf);
  if(n == 0)
    break;
  if(n < 0){
    fprintf(2, "read error\n");
    exit(1);
  }
  if(write(1, buf, n) != n){
    fprintf(2, "write error\n");
    exit(1);
  }
}

```

这段代码中最值得注意的一点是，`cat` 并不知道它是从文件、控制台还是管道中读取数据。同样地，`cat` 也不知道它是将数据打印到控制台、文件还是其他任何地方。文件描述符的使用，以及约定俗成的文件描述符 `0` 为输入、`1` 为输出的惯例，使得 `cat` 的实现变得非常简单。

`close` 系统调用释放一个文件描述符，使其可以被未来的 `open`、`pipe` 或 `dup` 系统调用（见下文）再次使用。**新分配的文件描述符总是当前进程中编号最小的、未被使用的描述符。**

文件描述符与 `fork` 的交互，使得 I/O 重定向的实现变得非常简单。`fork` 会将父进程的文件描述符表连同其内存一起复制，因此子进程在启动时，拥有与父进程完全相同的、已经打开的文件。而系统调用 `exec` 会替换调用进程的内存映像，但**会保留其文件描述符表**。这种行为允许 shell 在子进程中通过 `fork` 创建分支，然后关闭并重新打开选定的文件描述符，最后调用 `exec` 运行新程序，从而实现 I/O 重定向。以下是 shell 运行 `cat < input.txt` 命令时所执行代码的一个简化版本：

```c
char *argv[2];
argv[0] = "cat";
argv[1] = 0;

if(fork() == 0) {
  close(0);
  open("input.txt", O_RDONLY);
  exec("cat", argv);
}

```

在子进程关闭文件描述符 `0` 之后，接下来的 `open` 调用一定会使用该描述符来指向新打开的 `input.txt`：因为 `0` 是当前最小的可用文件描述符。随后 `cat` 程序执行时，它的文件描述符 `0`（标准输入）就已经指向 `input.txt` 了。父进程的文件描述符不会被这一系列操作所改变，因为这些操作只修改了子进程的描述符表。

xv6 shell 中用于 I/O 重定向的代码正是以这种方式工作的 (7931)。回想一下，在代码执行到这一步时，shell 已经 `fork` 出了一个子 shell，而 `runcmd` 将会调用 `exec` 来加载新程序。

`open` 的第二个参数由一组标志（flags）组成，以比特位的形式表示，用于控制 `open` 的行为。可能的值定义在文件控制 (`fcntl`) 头文件 (4000-4004) 中：`O_RDONLY`、`O_WRONLY`、`O_RDWR`、`O_CREATE` 和 `O_TRUNC`。它们分别指示 `open` 以只读、只写、或读写模式打开文件；如果文件不存在则创建文件；以及将文件截断为零长度。

现在应该很清楚为什么将 `fork` 和 `exec` 分离成两个系统调用是如此有用了：在这两次调用之间，shell 有机会对子进程的 I/O 进行重定向，而不会干扰主 shell 的 I/O 设置。我们可以想象一个假设的、将二者结合的 `forkexec` 系统调用，但使用这种调用来进行 I/O 重定向的方案似乎都很笨拙。比如，shell 可以在调用 `forkexec` 之前修改自己的 I/O 设置（然后再把它们改回来）；或者 `forkexec` 可以将 I/O 重定向的指令作为参数传入；或者（这是最糟糕的）让每一个像 `cat` 这样的程序都被设计成能够处理自己的 I/O 重定向。

虽然 `fork` 复制了文件描述符表，但每个底层的文件偏移量（offset）是在父子进程之间共享的。考虑以下示例：

```c
if(fork() == 0) {
  write(1, "hello ", 6);
  exit(0);
} else {
  wait(0);
  write(1, "world\n", 6);
}

```

在这段代码执行结束时，附加在文件描述符 `1` 上的文件将包含数据 `hello world`。父进程中的 `write` 调用（得益于 `wait`，它只在子进程结束后才运行）会从子进程 `write` 结束的位置继续写入。这种行为有助于在执行一连串 shell 命令时产生连续的输出，例如：`(echo hello; echo world) >output.txt`。

`dup` 系统调用会复制一个现有的文件描述符，返回一个新的文件描述符，该描述符指向相同的底层 I/O 对象。这两个文件描述符共享同一个偏移量，就像被 `fork` 复制出来的文件描述符一样。这是向文件写入 `hello world` 的另一种方式：

```c
fd = dup(1);
write(1, "hello ", 6);
write(fd, "world\n", 6);

```

如果两个文件描述符是通过一系列 `fork` 和 `dup` 调用从同一个原始文件描述符派生出来的，那么它们就会共享偏移量。否则，文件描述符不会共享偏移量，即使它们是由针对同一个文件的多次 `open` 调用产生的。`dup` 允许 shell 实现像这样的命令：`ls existing-file non-existing-file > tmp1 2>&1`。其中 `2>&1` 告诉 shell 分配给该命令一个文件描述符 `2`，它是文件描述符 `1` 的复制品。这样，现有文件的名称和不存在文件的错误信息都将出现在文件 `tmp1` 中。xv6 shell 尚不支持对错误文件描述符的 I/O 重定向，但现在你已经知道该如何实现它了。

文件描述符是一个强大的抽象，因为它们隐藏了自己所连接对象的底层细节：一个向文件描述符 `1` 写入数据的进程，它写入的目标可能是一个文件、一个像控制台这样的设备，或者是一个管道。
